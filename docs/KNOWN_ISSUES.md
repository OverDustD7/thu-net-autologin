# 已知限制

按「影响面」排序。每条都写清楚判据，不做模糊表述。

## 1. 凭据绑定机器与用户，换机器必须重跑

`ThuNet-pass.dpapi` 是 DPAPI（`CurrentUser`）密文，只能在**加密它的那个 Windows 用户 + 那一台机器**上解开。把文件拷到笔记本、或让同机器上的另一个用户读，都会解密失败。

这是设计选择而不是缺陷（无人值守要求机器能自动取用口令，就必然要有这个绑定），但它的后果必须记住：

- 换机器 → 重跑 `Set-ThuNetCredential.ps1`。
- 同机器换 Windows 用户 → 为新用户重跑。
- 重装系统 / 重建用户配置文件 → 重跑。

`Set-ThuNetCredential.ps1 -Show` 会明确报告「口令已设置但**在这里**解不开」，这是最直接的诊断。登录脚本在解不开时会写一条日志并请你去跑设置脚本，不会静默失败。

## 2. ac_id 只能「发现 + 兜底」，没有权威查询接口

`ac_id` 是墙口所属接入控制器的编号。没有可靠的官方查询接口，所以只能：

- 读缓存 → 看当前拦截暴露什么 → 扫浏览器历史 → 兜底候选。

后果：

- **刚换到一个新墙口、且没有任何浏览器访问过门户时**，前三条都可能拿不到真值，只能从兜底值（含 `173`、`1`）开始试。每个错值换回一个 `E2808`，成功的那个会被缓存。通常一两次就成功了，但**不保证第一次就对**。
- 如果门户拦截本身什么都没暴露、浏览器历史也没有，脚本只能试兜底值；这时在日志里会看到 `ac_id is not exposed by the interception`。
- 逆命题也成立：**缓存的 ac_id 会一直用下去**。搬机器/换端口之后如果缓存文件被一起搬走了，第一次尝试会用一个错值——它只会浪费一次请求（`E2808`），不会造成别的影响。

## 3. 「已认证」的判据依赖外部服务

`Test-LinkOnline` 用三个外部端点交叉验证，而且判据是严格的（`generate_204` 必须是 204，`connecttest.txt` 的内容必须逐字匹配，`baidu.com` 的响应体必须含 `baidu`）。

后果：

- 这三个端点中至少一个长期不可达时，一个**实际通着**的链路会被判成「未认证」，于是脚本会去尝试登录一次（登录本身通常也会因为 `ip_already_online_error` 或直接 `login_ok` 而无害地结束）。这不会断网，只会在日志里多几条。
- 反过来，一个**拦着流量但恰好放行了这三个端点**的门户会被判成「已认证」。现实中不存在这样的门户，但判据的上限就在这里。

## 4. 只处理 IPv4、只处理有线优先

- 只取 `InterNetwork`（IPv4）单播地址，不支持 IPv6 双栈认证（请求里 `double_stack=0` 是照门户页面自己的值写的）。
- 候选网卡排序是「以太网优先，其余按枚举顺序」。会跳过 `Loopback` / `Tunnel`，以及名字匹配 `Tailscale|vEthernet|WSL|Bluetooth` 的网卡。
  如果你的有线网卡被虚拟化软件改名成包含 `vEthernet` 的名字，它会被跳过——这时改那个正则（`Get-WiredAddress`）。
- 多块有线网卡时**每块都会各自判定、各自尝试登录**，这是刻意的（一块通不代表另一块通）。

## 5. 登录成功判据是 `error=ok`，不看 `ip_already_online_error`

脚本不把 `ip_already_online_error` 当成功（README 里有说明）。代价是：**当 IP 本来就在线、而外部端点又恰好判成「未认证」时**（见第 3 条），日志里会留下一条「这次登录没被当作成功」的记录，尽管 IP 实际是在线的。这是刻意选的方向——宁可多一条含糊的日志，也不要做出「我登录成功了」这种没有依据的断言。

## 6. 计划任务需要用户**登录后**才工作

任务的触发器是「用户登录时」+「每天定时」，主体是 `InteractiveToken`。所以：

- 机器开机但**停在登录界面没人登录**时，任务不会跑，网也不会自动认证。这是 `InteractiveToken` 的固有性质——也正因为它跑在用户会话里，DPAPI 口令才解得开。想在没有交互式登录时也认证，需要另一套凭据方案（比如把口令交给机器作用域的 DPAPI 或凭据管理器），本库没做。
- 休眠/唤醒**不会**触发登录触发器，靠的是每日触发器和看守自己那 60 秒一轮的循环。所以 `-IntervalSeconds` 不要设置得过大，否则唤醒后可能等很久才恢复。

## 7. 看守是「常驻进程」而不是服务

它随计划任务启动、随进程结束而消失。所以：

- 进程被强杀后靠 `RestartOnFailure`（1 分钟后，最多 3 次）拉回，之后要等下一个触发器。**没有做成 Windows 服务**，因为服务跑在 `LocalSystem` 下解不开用户作用域的 DPAPI 口令。
- 同一用户同时只能有一个看守（`Local\ThuNetAutoLoginWatcher` 互斥体 + 任务的 `IgnoreNew`）。第二个实例会直接退出并记一条日志。

## 8. 自检是「回归」而不是「与参考实现一致」

见 `docs/EVOLUTION.md` §3。`-SelfTest` 比对的是**内嵌的固定测试向量**，它证明「编码器没被改坏」，**不再证明**「编码器和 Python 参考实现逐字节一致」（原来调 `oracle.py` 时它证明后者）。

如果有人动了编码器，正确做法是拿真参考实现重新生成那三个常量，而不是用新输出覆盖常量。

## 9. 日志只有粗略轮转

`Write-Log` 在日志超过 256 KB 时保留最后 300 行（探针的捕获文件是 512 KB / 400 行）。不适合做长期趋势分析；它的用途是回答「刚才那一次为什么没成功」。

## 10. 没有做、也不打算做的事

- **不解析 `netsh`**（无控制台下的本地化输出问题，见 EVOLUTION §4.1）。
- **不做网络代理、不做断线重拨、不重启网卡**。它的职责边界就是「把门户认证上去」。
- **不改系统代理、不改 DNS、不装驱动、不碰显示设置**。
- **不自动更新**。要新版就自己拉。
- **不删、不改任何不是自己装的任务**。

## 11. 已确认但未修的小事

- `ThuNet-Probe.ps1` 的捕获文件里 `Get-NetIPConfiguration` 那段依赖 `NetTCPIP` 模块（Windows 8+ 自带）。该模块缺失时这一段被 `try/catch` 吞掉，捕获文件里就没有网卡信息，其余探测照常。**不影响登录脚本**（它完全不依赖该模块）。
- `-Status` 与 `-SelfTest` 都会跑一次 ac_id 发现（几个 8 秒超时的 HTTP 请求），所以它们**在链路封着的时候可能慢**（每个探测各等到超时）。链路已认证时它们很快。这是只读诊断为了给出真实结论而付的代价。

## 12. 自检向量里带着一个真实的校园网地址

`ThuNet-Login.ps1 -SelfTest` 的测试向量里，`info` 字符串的 `ip` 字段是 `59.66.18.167`——**抽取这个工具的那台机器当年的校园网地址**（DHCP 分配、不出校园、会回收）。它在这里只是**编码器的输入样本**：不是配置、不是凭据、不指向任何在线服务。

保留而没有换成文档保留地址（`192.0.2.x`）的理由：向量的价值在于「期望输出是**独立录下来的**」。一旦用本脚本自己的编码器去生成新向量的期望值，这个自检就再也不可能失败了——等于自己给自己出题。要换成中性地址，必须先用**独立实现**（参考实现 `github.com/WhymustIhaveaname/TsinghuaTunet` 的 `connect.py`）重算期望值。

把这条写下来，是为了让它是**有意识的选择**而不是漏掉。发布前审计脚本对这条模式的处理也是显式的：只有加 `-AcceptTestVectorIp` 才降级为接受，并在输出里打印理由。

这也是 §8 那条限制的具体体现——现在的自检证明的是「编码器没被改坏」，而不是「与参考实现一致」。

## 13. 改口令这条路的具体行为

- 看守**每轮重读凭据文件**，所以改完口令在默认 60 秒内生效，不必重启任务或机器。
- 凭据文件被改写时，看守清空失败计数与退避，日志里写 `credential files changed - failure counters and backoff cleared`。
- 口令改错而没更新这里时：同一接口**前两次失败各等 5 分钟，连续第 3 次起等 30 分钟**（日志 `blocked-backing-off(300s)` → `blocked-backing-off(1800s)`，第 3 次另写一行提示）。目的是不撞门户的失败计数，代价是「门户短暂抽风」这类情况恢复得慢一点。
- **不会**因为口令错误就永久放弃：30 分钟窗口一直重试，改对了立刻恢复。
