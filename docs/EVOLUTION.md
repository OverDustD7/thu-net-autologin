# 来历与关键决策

这份文档记录「为什么是现在这个样子」。规则只写结论的地方，这里写它背后的那次故障或那次测量。

## 0. 一句话

从一台无人值守主机（自习室机箱）上已经稳定运行的一套 srun 门户自动登录脚本里，把与那台机器绑定的一切剥离出来——凭据路径、显示/串流看守、日志名、互斥体名、Python 自检依赖——整理成一个可以公开、可以在别人机器上直接跑的产品。

## 2. 凭据：为什么单独一个脚本，为什么用 DPAPI

**为什么要拆。** 原脚本把「写凭据」和「用凭据」放在同一个文件、同一个入口开关里。用户自己的笔记本也要用，这就带来两个问题：

1. 想在笔记本上存凭据，就得把整个登录脚本（连同它那台机器专属的路径与日志名）拷过去；而如果笔记本上有人只想要「存一下账号」，他没有一个不需要理解协议就能用的入口。
2. 「登录脚本会写凭据」意味着一次误调用就可能覆盖掉正在工作的凭据。

拆开之后边界很清楚：

- `Set-ThuNetCredential.ps1` 是**唯一**的凭据写入者，交互式、要求二次确认、明确的成功/失败输出。
- `ThuNet-Login.ps1` 只读。凭据不在时它不猜、不生成、不覆盖，只让你去跑设置脚本。

**为什么用 DPAPI 而不是自己加密。** 需求是「无人值守，开机自己跑，不让人输口令」，所以口令必须以机器能自动取用的形式落盘。可选方案：

- 自己用一个密钥文件加密 → 那密钥文件本身就得保护，绕回去了。
- Windows 凭据管理器 → 可以，但它是个外部可读写的共享存储，而且 API 更绕；DPAPI 直接落在「这个用户在这台机器上」这个语义上。
- **DPAPI（`CurrentUser` 作用域）** → 密钥由 Windows 按用户+机器派生，不需要任何密钥文件；换用户、换机器都自动解不开。

最后一条既是优点也是代价，README 里把它写成了硬要求：**换机器必须重跑设置脚本**。

实现细节：`ConvertFrom-SecureString` 在不给 `-Key` 时就是用 `ProtectedData` 在 `CurrentUser` 作用域下加密的，输出是十六进制串。所以凭据文件是「DPAPI 密文的十六进制表示」。选它而不是直接调 `[System.Security.Cryptography.ProtectedData]` 写二进制，是为了和已经在这台机器上工作了两周的凭据文件**格式完全一致**——抽取过程必须能直接读旧文件做回归验证，不能因为换了存储 API 而让「新旧一致」这个判据失效。

`-Show` **不打印口令**，只打印账号名和「口令已设置」，以及一句更有用的话：这个口令文件**在这台机器/这个用户下能不能解开**。把 DPAPI 密文从别处拷进来的人，最需要的正是这一条诊断。

## 3. `-SelfTest`：为什么不再调 Python

原脚本的自检是拿本机 Python 跑 `oracle.py`（从 `TsinghuaTunet/connect.py` 逐字抄来的参考实现），再比对编码器输出的十六进制。它很硬气——比的是真参考实现，不是自己跟自己比。

但它和本库的两条硬约束冲突：**零依赖**（不能要求目标机装 Python）和**单文件可用**。

做法：把那一次真实比对的结果**录成常量**。测试用的 token 与 info 字符串是固定的，参考实现的输出就是固定的三个常量：

```
JSON      = {"username": "testuser", "password": "testpass", "ip": "59.66.18.167", "acid": 1, "enc_ver": "srun_bx1"}
ENC_HEX   = 94aca64aba9027ba06b0c67399e92be1950dd5aa0fb88ab65d813481500e70fcead4dbf6dc415a8a7d5393814cfb4d0387a03db7ea3168cdd9408e66be0aea2be19d6d86639f013208379246c9a9a9cb58f12fab891eb5222b9c8a837f0abd1de058146c408eda9247d660e7
INFO      = {SRBX1}p8xUmld+RE/Cb91zUrYlD1H0jO/gK2dIcZPtSuLyMgzdj0wI7PiOXqjFYDi9QttJTBL5fQ/6O971+2eUwSld8QCnWZ1kqvPxoJrmhbU3dMfZ4mQlXhBj2XKMX/0AoltnDiSHWPoyI3RNjUJq
```

`-SelfTest` 现在拿本机编码器算一遍，和这三个常量比。**代价要说清楚**：它验的是「编码器没被改坏」，不再是「编码器和参考实现一致」。用它在换机器、换 PowerShell 版本之后做体检是够的；但如果有人改了编码器，必须拿真参考实现（原来的 Python oracle）重新生成这三个常量，不能用新输出反过来覆盖常量——那样自检就变成了自己跟自己比，一点用都没有。

抽取过程中做了一次真回归：原脚本 `-SelfTest`（走 Python oracle）与新脚本 `-SelfTest`（走内嵌向量）**输出的十六进制与 `{SRBX1}` 串逐字符一致**，两边都判 `MATCH`。

## 4. 保留下来的三个「偶发坑」的修法

这三条都是**曾经真的踩过、修好、然后又被无意改回去过一次**的。抽取时逐字保留，并在代码里写明了证据。

### 4.1 无控制台进程解析不了 `netsh` 的本地化输出

现象：同一份脚本，从交互式窗口跑能认出两块网卡；被计划任务以无控制台方式拉起就报 `no usable interface address - nothing to do`，看守等于完全没工作。

定位过程：日志里 19:25:46 那次（交互式）两块网卡都解析成功，19:26:22 之后每一次（`Start-Process -WindowStyle Hidden` 拉起的）都失败。两次运行的唯一差别是**有没有控制台**，而 `netsh` 是按控制台的语言选输出语言的：交互式下给英文的 `Configuration for interface "..."` / `IP Address:`，无控制台下给本地化行，英文正则一条都匹配不上。

修法：改用 `[System.Net.NetworkInformation.NetworkInterface]::GetAllNetworkInterfaces()`，同样的数据、任何语言环境一致、不需要解析文本。原 `netsh` 那段作为「仅参考」保留在函数末尾、在 `return` 之后（不可达）。

### 4.2 用 `-f` 构造 JSON 会被字面花括号坑

现象：服务端回 `auth_info_error`。

原因：`info` 字段是个 JSON 对象，字符串里全是字面的 `{` `}`。`-f` 会把 `{...}` 当格式项，抛 `Input string was not in a correct format`，于是 `$infoJson` 成了空串，签名自然失败。而且那个错误发生在表达式求值里，最容易被 `$ErrorActionPreference = 'Continue'` 吞掉。

修法：字符串拼接。并且要求拼出来的 JSON 和 Python `json.dumps` 的默认写法**逐字节一致**（`":"` 后有空格、`", "` 后有空格、字段顺序一致），因为编码器输出是要跟 Python 参考实现逐字节比对的。

### 4.3 请求要绕代理，绑定委托不能无限重试

两件事一起说，因为它们是同一个函数里相邻的两处。

- **`$req.Proxy = $null`**：校园门户走本地链路，让它穿本机 HTTP 代理是错的；更关键的是，代理客户端缺失的时刻（刚开机、刚崩溃）正好就是自动登录最需要工作的时刻。
- **绑定源地址**（`Set-BindDelegate`）：`get_challenge` 回显服务端看到的地址，登录认证的就是那个地址。请求若从 WiFi 兜底出口出去，认证上的是 WiFi 地址，有线口依然封着——而所有连通性探测都会报「在线」，因为 WiFi 通。所以「探测」和「登录」都必须绑到有线网卡上才说明问题。
- **但**：`BindIPEndPointDelegate` 只要返回端点，框架就一直重试；只有返回 `$null` 才放弃。原来无条件返回端点，于是每一次失败连接都变成一个占满一个核的忙重试循环——表现就是 `-Status` 挂住（它对 `http://4.5.6.7` 的发现探测在门户已认证后是不会有应答的）。修法：重试 2 次后返回 `$null`，让请求正常报错。

## 5. 抽取过程中自己引入的两个 bug（都已修）

**抽取不等于安全。** 新写的那部分代码引入了两个在解析阶段完全看不出来的错误，都是靠真机跑出来的：

### 5.1 只读入口一行输出都没有

第一版里「是否安静」是一个标志位，只读入口（`-Status` / `-SelfTest`）把它设成了「安静」——方向反了，于是这两个入口**什么都不打印**。而它看起来完全正常：进程退出码 0、没有任何异常、日志照写。一个只读诊断工具不输出，和「它根本没运行」在外部观察上是同一件事。

修法是结构性的：拆成两个函数。`Write-Out` 永远输出（给用户要看的只读诊断与单次结果用），`Write-Line` 只在看守模式把控制台接管之后才闭嘴。**没有标志位，就没有设反的可能。**

### 5.2 `-CredentialDir` 悄悄丢掉了已学到的 ac_id

原脚本把 ac_id 缓存在 `portal-acid.txt`，新脚本第一版用 `ac_id.txt`，而且只查新名字。于是「把 `-CredentialDir` 指向一个旧目录」这个用法下，缓存**静默失效**，ac_id 退回当前拦截暴露的值——在那台机器上正好是服务端的默认值 `1`，而那个口的真值是 `173`。症状是 `-Status` 报 `ac_id : 1`，而原脚本报 `173`；**回归测试就是靠这个不一致发现的**。

修法有三层：

1. 凭据**和** ac_id 缓存都做旧名字别名（`portal-*` → `ThuNet-*`），读旧名、写规范名。
2. ac_id 缓存从凭据目录挪到安装根目录（`%LOCALAPPDATA%\ThuNetAutoLogin\`）——它是机器本地状态、不是凭据，而凭据目录允许是只读的旧位置。给 `-CredentialDir` 时仍然会**读**那里的缓存。
3. 缓存命中时写一条日志，说明值是从哪个文件读来的，免得下次再出现「它为什么挑了这个数」。

## 6. 为什么入口是这些样子

- **`-Once` 是默认动作**，不是独立模式：不带开关跑一次就是一次登录尝试。`-Once` 只是把它写明白，便于脚本化调用。
- **`-MaxRuns`（默认 0 = 不限次）**：存在理由是**可测试性**。「跑两轮然后退」让看守循环能被真正执行一遍并确认它会退出——否则验证一个无限循环只能靠杀进程，那证明不了它自己能正常收尾。它同时也能表达「对这个顽固的口试几次就放弃，交给每日触发器再试」。
- **`-Watch` 里 `MaxRuns` 的收尾放在 `finally`**：互斥体必须在退出前释放。否则限次跑完之后，紧接着的第二次运行会以「already running」退出——看起来和循环坏掉一模一样。
- **互斥体是 per-user 的 `Local\...`**：按用户隔离就够（同一用户不需要两个看守抢着登同一个口），而且不需要管理员权限。

## 7. 计划任务：为什么用 `schtasks` 而不是 cmdlet

一条硬性经验，来自这台机器上其它脚本的反复教训：

> `Register-ScheduledTask` 的失败是**非终止错误**。`try/catch` 抓不到它；`$?` 也不可靠。于是围着它写 try/catch 的安装脚本，会在什么都没装上的情况下打印「安装成功」。

`schtasks` 是外部程序，结果是真实进程退出码。本库的安装脚本每次调用后立刻读 `$LASTEXITCODE`，失败就把退出码打出来并且不撒谎；注册成功后还会 `schtasks /query /tn <名> /xml` **读回来确认**——「调用没报错」不等于「任务按意图存在了」。

两个附带的坑：

- `schtasks /create /xml` 要求 XML 文件是 **UTF-16LE 带 BOM**。给 UTF-8 文件会报「task XML contains a value which is incorrectly formatted or out of range」，读起来像内容问题，其实是编码问题。
- 动作一律走 `wscript.exe RunHidden.vbs <脚本> ...`。直接写 `powershell.exe -WindowStyle Hidden` 会创建控制台窗口（闪一下黑框，而且如果 `-Watch` 启动参数写错，那个黑框会一直留着）。

任务定义单独放在 `ThuNet-TaskXml.ps1` 里，就是为了能在**不注册任何任务**的前提下检查它：`Install-ThuNetAutoLogin.ps1 -WhatIf` 打印完整 XML 后停止。往一台正在远程使用的机器上注册一个「每次登录都触发」的任务，不该是测试的一部分。

## 8. 安全边界（明确不做的事）

- 不装模块、不下载任何东西、不改系统代理、不改 DNS。
- 不动任何**不是自己装的**计划任务。卸载脚本先读回任务 XML、确认动作指向本仓库目录才删。
- 不留任何后台常驻进程（看守只存在于计划任务启动的那个进程里，随任务结束而消失）。
- 凭据只落到用户自己的 `%LOCALAPPDATA%`。唯一会请求管理员权限的操作是 `-RunLevel Highest`，而且那需要用户自己从提权窗口跑。

## 9. 一个双击入口，与「改了口令」这条闭环（2026-10-22 追加）

要求是「点一个脚本就一次性搞定」，以及「以后可能改账号口令，也要考虑好」。对应的补充：

- `Setup-ThuNetAutoLogin.cmd` → `Setup-ThuNetAutoLogin.ps1`：凭据 → 注册任务 → **立刻启动** → 验证，四步一次做完，幂等可重跑。双击 `.ps1` 在 Windows 上是拿记事本打开，所以**可点的入口必须是 `.cmd`**；`.cmd` 里的 `-ExecutionPolicy Bypass` 只对那一个进程生效，不改系统设置。
- `Change-ThuNetCredential.cmd`：等于 `Setup-ThuNetAutoLogin.ps1 -ForceCredential`，改口令走它。
- 这两条**不重复实现任何逻辑**：凭据写入仍然只有 `Set-ThuNetCredential.ps1` 一处，任务 XML 仍然只有 `ThuNet-TaskXml.ps1` 一处，Setup 只是按顺序调用它们。调用走**独立进程**，这样被调脚本的 `exit` 不会结束 Setup，退出码也是真实的进程退出码。

**为什么没有「开机（未登录）就联网」这个选项**：口令是 DPAPI `CurrentUser` 加密，登录前没有令牌可解密，这种任务连口令都读不出来。要做到登录前就跑，只能把口令降级成机器可读、或写进任务定义，两者都意味着机器上任何进程都能拿到它。默认不做，理由与取舍写在 README。

**改口令这条闭环的两个要点**（这次新加；此前只有「每轮重读凭据文件」这一半）：

1. **凭据文件一变，失败计数与退避立刻清空。** 少了这条，改完口令还要等旧口令挣来的退避窗口，用户看到的就是「工具没理我」。
2. **连续失败退避升级**：同一接口前两次失败各等 5 分钟，连续第 3 次起等 30 分钟，并在第 3 次时单独写一行日志，明确指出「若口令已改，用 `Set-ThuNetCredential.ps1` / `Change-ThuNetCredential.cmd` 更新」。动机是**门户会计数失败尝试**——口令改错时不该用每天 288 次的频率去撞它。5 分钟那一档留给短暂故障（门户维护、网口刚插上），那类问题恢复得比 30 分钟快。

这两条都做过真机验证：`Get-LoginBackoffSeconds` 按 AST 从交付文件里抽出来直接调用（1、2 次 → 300 秒，3 次起 → 1800 秒），`Get-CredentialStamp` 在同一目录下能感知文件被改写；`Repair-Once` 内部「先清空、后算窗口」的顺序也用 AST 核对过。
